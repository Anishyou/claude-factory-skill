# Software Factory for Claude Code

A small, visual software factory built from one Claude Code skill, eleven
subagents, three hooks and plain markdown files. `/factory init` interviews
you about the stack and sets the repo up. You point `/factory plan` at a
product brief and get a roadmap and a backlog. For every milestone with
screens, a designer produces static mockups that you approve before any UI
is built. `/factory next` takes the
next job: agents write a spec, write failing tests, build it on its own
branch, review it, and open a pull request for you to merge. After a
milestone, `/factory verify` checks the merged work against the brief as a
whole and writes a coverage report; gaps go back into the backlog.

```
brief ─ /factory init ─► you choose the stack (interview) ─► docs/stack.md, CLAUDE.md, scaffold job
      ─ /factory plan ─► planner ─► roadmap.md + backlog.md
                                        │
         milestone with screens ─► designer ─► static mockups ─► YOU approve ─► docs/design/<M>/
                                        │ /factory next        (UI jobs wait for this)
feature → spec-writer → test-writer → builder → [security, (ux, ui), code] → WAIT FOR ALL
                                         ▲          (gate hook)                 │
                                         └──── any CHANGES: resume builder ◄────┤
                                                                                ▼ all PASS
                                   open PR ◄─ APPROVE ─ approver ─ ESCALATE → needs-human
                                      │
                       you merge on GitHub → /factory close → merged
                                                        │ milestone done
                              /factory verify ─► verifier ─► coverage.md (+ gaps → backlog)
```

It is a fork of [zazencodes' software factory](https://github.com/zazencodes/zazencodes-season-3/tree/main/src/software-factory-claude-code)
with three changes that matter for production use:

1. **Gates are enforced by hooks, not prompts.** A builder cannot finish on
   red tests, a dirty tree, or a change to a protected path. Agents cannot
   edit secrets, lockfiles, CI, deploy config or migrations, and cannot
   force-push, push to `main`, merge locally or deploy. These hold in every
   permission mode, including `--dangerously-skip-permissions`.
2. **An independent test-writer** writes failing tests from the spec before
   the builder sees it. The builder must make them pass; the code reviewer and
   approver check the builder didn't weaken them.
3. **No local auto-merge.** `APPROVE` pushes the branch and opens a PR with
   the full factory record in its body. Branch protection, CI and a human are
   the last gate. `/factory close` cleans up after you merge.

This folder is laid out like a repo root, so you can copy it straight into yours.

```
.claude/
  settings.json                  hooks + a starter permission allowlist
  hooks/
    session-start.py             exposes $FACTORY_SESSION_ID so parallel jobs stay apart
    guard.py                     PreToolUse: protected paths, main-checkout writes, forbidden commands
    gate.py                      SubagentStop: branch clean, no protected changes, validation green
    _factory.py                  shared helpers
  skills/factory/SKILL.md        the orchestrator: runs the loop, writes job.json
  agents/
    planner.md                   opus    brief → roadmap.md + backlog.md
    designer.md                  opus    milestone → static HTML/CSS mockups + design.md, iterated until you approve
    spec-writer.md               opus    writes spec.md (Covers / Surfaces / Owns header)
    test-writer.md               sonnet  writes failing tests + tests.md
    builder.md                   opus    commits on factory/<job-id>, writes build.md
    reviewer-security.md         opus    writes round-N/review-security.md
    reviewer-ux.md               sonnet  writes round-N/review-ux.md
    reviewer-ui.md               sonnet  writes round-N/review-ui.md
    reviewer-code.md             sonnet  writes round-N/review-code.md
    approver.md                  opus    writes decision.md (applies docs/policies.md)
    verifier.md                  opus    milestone → verify.md + factory/coverage.md
factory/
  factory.config.json            validation commands, protected paths, forbidden commands
  roadmap.md                     the plan (generated)
  backlog.md                     queue for /factory next (generated from the roadmap)
  coverage.md                    the product meter (generated by verify)
docs/policies.md                 standing decisions agents apply instead of escalating
docs/stack.md                    the stack decisions from /factory init
docs/design/<milestone>/         approved mockups + design.md (committed through a PR)
  dashboard.html                 the visual board
  jobs/                          one folder per job (runtime state, gitignored)
CLAUDE.factory-template.md       the sections your CLAUDE.md needs
```

## How it works

- The Claude Code session that runs `/factory` becomes the orchestrator. It
  spawns every agent and is the only writer of the job's `job.json`.
- Agents get their context from files, not the conversation, and each writes
  only its own file. Every status file starts with a machine-checkable line:
  `STATUS: READY|BLOCKED`, `STATUS: WRITTEN|SKIPPED`, `VERDICT: PASS|CHANGES`,
  `GATE: PASS|FAIL`, `APPROVE|ESCALATE`.
- Each job gets its own git worktree next to your repo
  (`../<repo>-factory/<job-id>/`) on a `factory/<job-id>` branch. Open several
  Claude sessions and run `/factory` in each to build features in parallel.
- The four reviewers run in parallel. A round is done only when all four files
  exist. If any says CHANGES, the same builder is resumed (at most twice).

### The hooks

| Hook | Event | What it does |
| --- | --- | --- |
| `guard.py` | `PreToolUse` on Edit/Write/Bash | Denies edits to `protectedPaths` (unless `allow.md` unlocks them), denies code edits in the main checkout while a job runs, denies any Bash command matching `forbiddenCommands`. |
| `gate.py` | `SubagentStop` on `builder`, `test-writer` | Checks the status file's first line, that the worktree is on the job branch and clean, that no protected path changed on the branch, that the test-writer only touched `testPaths`, then runs every `validation` command for the phase. On failure the agent is sent back with the output and keeps working. Writes `gate.md`. |
| `session-start.py` | `SessionStart` | Writes `FACTORY_SESSION_ID` to the session's env so hooks can tell parallel jobs apart. |

A hook deny holds regardless of permission mode. Agents are told not to work
around a denial and to write `STATUS: BLOCKED` instead, which routes the job
to you.

## Commands

```
/factory init [brief]              interview: stack, db, auth, hosting, tests → docs/stack.md, CLAUDE.md, scaffold job, then plan
/factory plan [brief] [milestone]  brief → roadmap + backlog (re-run after a verify to re-plan)
/factory design <milestone>        designer produces static mockups for the milestone's screens
/factory design rework <job> <note>  send the mockups back with your notes (no round limit)
/factory design approve <job>      commit the mockups to docs/design/<milestone>/ via a PR; UI jobs unlock when merged
/factory next                      run the first backlog item whose dependencies are merged
/factory <feature>                 run an ad-hoc job through the loop
/factory verify [milestone]        product gate: run the stack, walk the brief's scenarios, write coverage.md
/factory approve <job-id>          open the PR for a needs-human job
/factory rework <job-id> <note>    send a job back to the builder with feedback (also for PR comments)
/factory allow <job-id> <path>     unlock a protected path for one job, then continue
/factory close <job-id>            after you merge the PR: remove worktree + branch
/factory status                    coverage line, one line per job, backlog state
```

## From brief to product

The feature loop proves each PR. Five things make the sum of the PRs add up
to the product in the brief:

- **The interview** (`/factory init`) happens before any loop runs. The
  orchestrator reads the brief and asks you, with a recommendation and a
  reason each, about language and framework, database, auth, jobs, storage,
  hosting, test runner and CI. The answers become `docs/stack.md`, the
  `CLAUDE.md` sections every agent reads, and the validation commands the
  gate runs. "Decide later" is allowed and lands in the roadmap.
- **Design before build.** A milestone that adds screens gets a design job
  first. The designer writes plain HTML/CSS mockups with real content, one
  file per screen, states switchable, `data-component` names on every
  region. You open them from the dashboard, send notes with `/factory design
  rework`, and approve with `/factory design approve`, which commits them to
  `docs/design/<milestone>/` through a PR. Only then can UI jobs start. The
  builder implements the approved screens in the real stack and never
  copies the HTML; the UI reviewer puts the built screen next to the mockup.

- **The planner** reads the whole brief and writes `factory/roadmap.md`:
  milestones, jobs with the requirement IDs they cover, dependencies, the
  paths each job owns (so parallel jobs don't collide), and the protected
  paths it will need. The backlog is generated from it; you edit the roadmap,
  not the backlog. Open questions land in a **Decisions needed** list you
  answer once, in `docs/policies.md`.
- **The verifier** runs after a milestone: fresh checkout, full stack with
  mock providers, every acceptance scenario the brief names, and a table of
  every requirement ID → job → named test. The first line of
  `factory/coverage.md` is the number you track (`COVERAGE: 71% · M0 · …`).
  Gaps become backlog items and go through the normal loop.
- **Policies** turn repeated escalations into standing rules: approved
  dependencies, default limits, what counts as a deploy change, what always
  goes to a human. The approver cites the section instead of asking.

Specs now carry a machine-read header (`Covers`, `Surfaces`, `Owns`,
`Policies`). `Surfaces: api` skips the UX and UI reviewers; tests are grouped
in `describe("<ID> …")` blocks so coverage can be traced without guessing.

## Use it in your repo

1. Copy `.claude/` and `factory/` into your repo root. If you already have a
   `.claude/settings.json`, merge the `hooks` and `permissions` blocks.
2. Edit `factory/factory.config.json`:
   - `validation`: your real lint / typecheck / test / build commands.
     `phases` says which run after the test-writer (`tests`) and after the
     builder (`build`). Lint and typecheck usually run in both; the test
     command only in `build`, since the tests are meant to fail before it.
   - `testPaths`: where tests live, so the test-writer can't touch anything else.
   - `protectedPaths` and `forbiddenCommands`: tighten or loosen for your stack.
3. Add `factory/jobs/` to your `.gitignore`. Job folders are runtime state.
4. Make sure your `CLAUDE.md` has the sections in `CLAUDE.factory-template.md`:
   fresh-checkout setup, dev server on a given port, validation commands,
   test layout, conventions. The agents carry nothing repo-specific.
5. Install the [`gh`](https://cli.github.com/) CLI and log in; the factory
   opens PRs with it. Turn on branch protection for `main` so a PR is the
   only way in.
6. Install the [`agent-browser`](https://github.com/vercel-labs/agent-browser)
   CLI if your project has pages to look at. The builder and the UX and UI
   reviewers use it to check the running app.
7. Extend `permissions.allow` in `.claude/settings.json` with your stack's
   commands (`npm *`, `pytest *`, …) so subagents don't stall on prompts.
8. Commit everything on `main`, then run `/factory <feature>`.

The review checklists are deliberately general. Ask Claude to tailor them to
your stack: your framework, your security hot spots, and what the approver
should always escalate.

## Dashboard

```bash
cd factory && python3 -m http.server
```

Open <http://localhost:8000/dashboard.html>. Jobs move across the stages as
cards, the tests/gate marks and review chips fill in as results land, PR-open
jobs link to GitHub, and jobs that need you stand out. Click a card to read its
markdown files. It polls every two seconds, so leave it open while jobs run.

## Testing the hooks without a job

```bash
export CLAUDE_PROJECT_DIR=$PWD
echo '{"tool_name":"Bash","tool_input":{"command":"git push --force origin x"}}' | python3 .claude/hooks/guard.py; echo "exit $?"
echo '{"tool_name":"Bash","tool_input":{"command":"git merge factory/001-x"}}'   | python3 .claude/hooks/guard.py; echo "exit $?"
```

Both should print a reason and `exit 2`. Protected-path denials only apply
inside a job worktree, or in the main checkout while the session is running a
job, so a normal session in your repo can still edit CI config by hand.

## Costs and caveats

- Each job is roughly: 1 opus spec, 1 sonnet tests, 1–3 opus builds, 4
  reviews per round (1 opus, 3 sonnet), 1 opus approval. The gate re-runs your
  full validation after every build round; keep those commands fast or scope
  them.
- The gate trusts `factory.config.json`. Agents are told not to edit it and the
  guard denies it, but a human reviewing the PR should still glance at the diff
  for anything under `factory/` or `.claude/`.
- Hooks need `python3` on PATH. No other dependencies.
- `SubagentStop` hooks need Claude Code with subagent `agent_type` in hook
  input (any recent version). If the gate ever logs "could not find this
  session's active job", the orchestrator forgot to write `session` into
  `job.json`; the gate skips rather than blocks in that case, so fix it.
